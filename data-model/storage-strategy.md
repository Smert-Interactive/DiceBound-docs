# Стратегия хранения данных DiceBound

## Назначение

Этот документ фиксирует, какие данные DiceBound хранятся в реляционных
столбцах PostgreSQL, какие данные хранятся в `JSONB` и почему выбран такой
подход.

Главный принцип:

- реляционные столбцы хранят идентификаторы, связи, владение, права доступа,
  версии и служебные поля;
- `JSONB` используется только для schema-driven данных, структура которых
  зависит от RPG-системы и её версии;
- внешние ключи, владение и права доступа не прячутся внутри JSON-документов.

## Краткое решение

DiceBound использует гибридную модель хранения:

- PostgreSQL relational model хранит устойчивую структуру приложения;
- PostgreSQL `JSONB` хранит только schema-driven данные, форма которых зависит
  от RPG-системы и её версии.

В текущем ядре `JSONB` используется только в двух местах:

- `system_versions.schema`;
- `character_versions.data`.

Все остальные основные данные остаются реляционными.

## Что хранится реляционно

В обычных столбцах PostgreSQL должны храниться:

- primary keys;
- foreign keys;
- идентификаторы пользователей;
- владельцы сущностей;
- названия систем и персонажей;
- номера версий;
- права доступа;
- даты создания и изменения;
- авторы изменений, если они отслеживаются;
- другие данные, для которых важны ограничения базы.

Для таких данных важны:

- `PRIMARY KEY`;
- `FOREIGN KEY`;
- `UNIQUE`;
- `CHECK`;
- индексы;
- предсказуемые SQL-запросы.

## Что хранится в JSONB

В `JSONB` хранятся только schema-driven данные:

- `SystemVersion.schema`;
- `CharacterVersion.data`.

Эти данные зависят от RPG-системы. У Dungeons & Dragons, Cyberpunk RED,
Call of Cthulhu или пользовательской системы могут быть разные листы
персонажей и разные наборы полей.

`JSONB` не используется для того, чтобы спрятать всю модель данных в один
документ.

## Способ хранения по сущностям

### User

Способ хранения: реляционные столбцы.

Примеры полей:

- `id`;
- `username`;
- `email`;
- `created_at`;
- `updated_at`.

Обоснование:

- пользователь является устойчивой сущностью;
- `User` участвует во внешних ключах;
- по пользователю нужны проверки уникальности и связи;
- хранение пользователя в `JSONB` усложнило бы владение и права доступа.

`User` не хранит данные, зависящие от схемы RPG-системы.

### GameSystem

Способ хранения: реляционные столбцы.

Примеры полей:

- `id`;
- `owner_id`;
- `name`;
- `description`;
- `created_at`;
- `updated_at`.

Обоснование:

- RPG-система является отдельной сущностью;
- владелец системы хранится через `owner_id`;
- версии системы связываются с ней через внешний ключ;
- систему нужно искать, отображать и связывать с персонажами.

Гибкая структура листа персонажа не хранится в `GameSystem`. Она находится в
`SystemVersion.schema`.

### SystemVersion

Способ хранения: реляционные столбцы и одно поле `JSONB`.

Реляционные поля:

- `id`;
- `game_system_id`;
- `version_number`;
- `created_by_user_id`;
- `created_at`.

JSONB-поле:

- `schema`.

Обоснование:

- `SystemVersion` должна быть связана с `GameSystem`;
- номер версии должен быть уникален внутри одной RPG-системы;
- автор и дата создания являются служебными данными;
- сама структура листа персонажа может отличаться между системами.

`schema` хранит описание полей листа персонажа для конкретной версии
RPG-системы.

Пример:

```json
{
  "fields": {
    "health": {
      "type": "integer",
      "label": "Health"
    }
  }
}
```

Почему это `JSONB`:

- разные RPG-системы имеют разные наборы полей;
- пользовательские системы могут иметь неизвестную заранее структуру;
- изменение структуры системы должно создавать новую `SystemVersion`;
- новая структура не должна требовать миграции базы данных.

### Character

Способ хранения: реляционные столбцы.

Примеры полей:

- `id`;
- `owner_id`;
- `game_system_id`;
- `name`;
- `created_at`;
- `updated_at`.

Обоснование:

- `Character` является стабильной сущностью персонажа;
- владелец персонажа должен быть доступен через foreign key;
- RPG-система персонажа должна быть доступна через foreign key;
- изменяемое состояние персонажа хранится не здесь, а в версиях.

`Character` не должен хранить весь лист персонажа в `JSONB`.

### CharacterVersion

Способ хранения: реляционные столбцы и одно поле `JSONB`.

Реляционные поля:

- `id`;
- `character_id`;
- `system_version_id`;
- `version_number`;
- `created_by_user_id`;
- `created_at`.

JSONB-поле:

- `data`.

Обоснование:

- `CharacterVersion` должна быть связана с конкретным `Character`;
- `system_version_id` фиксирует схему интерпретации данных;
- номер версии должен быть уникален внутри одного персонажа;
- автор и дата создания являются служебными данными;
- значения листа персонажа зависят от `SystemVersion.schema`.

`data` хранит значения конкретного состояния персонажа.

Пример:

```json
{
  "health": 35,
  "inventory": [
    {
      "name": "Sword",
      "quantity": 1
    }
  ]
}
```

Почему это `JSONB`:

- поля персонажа зависят от выбранной RPG-системы;
- структура данных определяется `SystemVersion.schema`;
- разные версии системы могут иметь разные схемы;
- исторические версии персонажа должны хранить значения в прежней форме.

### Share

Способ хранения: реляционные столбцы.

Примеры полей:

- `id`;
- `character_id`;
- `user_id`;
- `permission`;
- `created_at`.

Обоснование:

- `Share` описывает права доступа;
- связь `Character -> User` должна быть проверяемой через внешние ключи;
- пара `character_id`, `user_id` должна быть уникальной;
- `permission` должно проверяться ограничениями или прикладной логикой.

`Share` не должен храниться в `JSONB`, потому что права доступа являются
структурными данными приложения.

## Schema и Permission

`Schema` не является отдельной таблицей.

Она хранится в поле `SystemVersion.schema` с типом `JSONB`.

`Permission` также не является отдельной таблицей.

Уровень доступа хранится в реляционном поле `Share.permission`.

Таким образом, структура схемы и данные листа используют `JSONB`, а права
доступа остаются частью реляционной модели.

## Почему не хранить все в JSONB

Хранение всей модели в `JSONB` привело бы к проблемам:

- foreign keys оказались бы скрыты внутри JSON;
- сложнее было бы проверить ownership;
- сложнее было бы ограничить permissions;
- сложнее было бы обеспечить уникальность версий;
- исторические связи могли бы стать неоднозначными;
- SQL-запросы стали бы менее предсказуемыми.

Поэтому `JSONB` используется только там, где гибкость действительно нужна.

## Правила для новых полей

Новое поле должно быть реляционным, если оно:

- идентифицирует сущность;
- связывает сущности;
- описывает владельца;
- описывает права доступа;
- участвует в сортировке или фильтрации;
- требует `UNIQUE`, `CHECK` или `FOREIGN KEY`;
- является служебным полем.

Новое поле может быть `JSONB`, если оно:

- зависит от RPG-системы;
- определяется `SystemVersion.schema`;
- может иметь разную структуру в разных системах;
- является частью состояния листа персонажа.

## Итог

Стратегия хранения DiceBound разделяет устойчивую структуру приложения и
изменяемые данные, специфичные для RPG.

Реляционно хранятся:

- сущности;
- идентификаторы;
- связи;
- владение;
- права доступа;
- номера версий;
- даты;
- авторы изменений.

В `JSONB` хранятся:

- `SystemVersion.schema`;
- `CharacterVersion.data`.

Такой подход сохраняет целостность данных PostgreSQL и одновременно позволяет
поддерживать разные RPG-системы без создания отдельных таблиц под каждую
конкретную игру.
