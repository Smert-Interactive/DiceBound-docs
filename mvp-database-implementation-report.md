# DiceBound MVP: отчёт о реализации базы данных

Документ фиксирует результат реализации и проверки слоя хранения DiceBound
MVP.
Он предназначен для передачи результата команде и дальнейшей интеграции с
backend.

Состояние на 17 октября 2026 года: модель хранения и начальные данные
реализованы, развёрнуты в серверной PostgreSQL и проверены.

## Основания и область работы

Реализация подготовлена для задачи по хранению данных DiceBound MVP на основе:

- [ERD](./erd.md), задача [#10][erd-task].
- [Контракта SheetSchema](./sheet-schema.md), задача [#33][schema-task].
- [Утверждённого MVP](../mvp-scope.md), задача [#30][mvp-task].

Выполнены SQL-миграции, ограничения целостности, seed встроенных систем,
команды запуска, документация и автоматические проверки.
Файлы реализации подготовлены в локальном проекте DiceBound-backend; их
передача и включение в общую ветку backend согласуются отдельно.
Этот документ фиксирует результат работы с БД.

## Модель хранения

Добавлены четыре миграции.
Каждая содержит `.up.sql` для применения и `.down.sql` для отката.

| Миграция | Сущности |
| --- | --- |
| `001_users` | User |
| `002_game_systems` | GameSystem, SheetSchema |
| `003_characters` | Character, CharacterVersion |
| `004_character_shares` | CharacterShare |

Создаются шесть бизнес-таблиц: `users`, `game_systems`, `sheet_schemas`,
`characters`, `character_versions`, `character_shares`.
Служебная таблица `schema_migrations` хранит историю применения и контрольные
суммы миграций.

Использован JSONB для `sheet_schemas.schema`, `characters.data` и
`character_versions.data`.
Значения должны быть JSON-объектами; для схемы также проверяется наличие
массива `sections`.

Реализованы следующие ограничения:

- Внешние ключи между пользователями, системами, схемами, персонажами,
  версиями и записями доступа.
- Уникальность email с приведением к нижнему регистру и удалением пробелов по
  краям.
- Положительный номер версии, уникальный внутри персонажа.
- Одна запись доступа для пары «персонаж / получатель».
- Соответствие схемы системе персонажа через составной внешний ключ.
- Защита опубликованных схем, сохранённых снимков и полей происхождения копии
  от изменения.

Поле `password_hash` обязательно и не может быть пустым.
Хеширование пароля выполняется будущим Auth-сервисом; БД не вычисляет хеш и не
проверяет его криптографический формат.

### Системы и удаление импортов

Предусмотрены `BUILTIN` и `IMPORTED`.
Встроенные системы имеют уникальный код, импортированные — владельца.

Импортированная система удаляется из доступных через `deleted_at`.
Создание новых обычных персонажей на ней блокируется, а используемые схемы,
существующие персонажи и история сохраняются.
Повторный импорт создаёт новые записи вместо восстановления старой системы.

### История и доступ

Версии хранят полные снимки состояния.
Проверен сценарий восстановления выбранной версии с удалением более поздних
снимков без создания новой версии.

Для VIEW предусмотрен `history_visible`, по умолчанию `false`.
VIEW можно отозвать удалением записи доступа.

EDIT предполагает независимую копию с собственными данными и историей.
Хранятся ссылка на оригинал, ссылка на исходного владельца, снимок его имени и
время копирования.
После удаления оригинала копия и её история сохраняются, а ссылка на оригинал
очищается.
Прямой отзыв записи EDIT запрещён.

Создание персонажа вместе с первой версией, сохранение, восстановление и
передача EDIT выполняются сервисами в транзакциях.
Ограничения БД поддерживают эти операции; сами миграции не создают снимки или
копии автоматически.

## Начальные данные и SheetSchema

Seed добавляет две встроенные системы и по одной схеме с фиксированными UUID:

| Код системы | Схема листа | Секций |
| --- | --- | --- |
| `dnd-5e-mvp` | D&D 5e MVP v1 | 3 |
| `call-of-cthulhu-mvp` | Call of Cthulhu MVP v1 | 4 |

D&D использует секции Basic, Abilities и Combat.
Call of Cthulhu использует Investigator, Characteristics, Resources и Skills.

Схемы имеют разную структуру и используют единый формат `sections → fields`.
Поддержаны согласованные типы `text`, `number`, `select`, `checkbox`,
`resource`, `calculated`.
Проверены уникальность ID полей, параметры полей и ссылки в формулах.

D&D включает уровень, класс, шесть характеристик и модификаторы, HP, AC и
Inspiration.
Call of Cthulhu включает профессию, возраст, восемь характеристик, HP, Sanity,
Luck, Unconscious и три навыка.
В обеих схемах есть имя персонажа.
Это упрощённые листы MVP.

Повторный seed не создаёт дубликаты и не обновляет даты существующих записей.
Расхождение опубликованных данных с seed вызывает ошибку вместо перезаписи.
Добавление данных выполняется в одной транзакции.
Пользователи, персонажи, версии и записи доступа не создаются seed-командой.

## Запуск и воспроизводимость

В подготовленной реализации предусмотрены команды из корня backend-проекта:

```sh
npm run db:status
npm run db:migrate
npm run db:seed
npm run test:db
```

Для отката последней миграции предусмотрена команда `npm run db:rollback`.
Откат удаляет соответствующие таблицы и данные и предназначен для
контролируемого применения.

Подключение задаётся переменными `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`,
`PGPASSWORD`.
Локальная настройка и описание ограничений подготовлены в документации
backend.
Для Windows PowerShell можно использовать `npm.cmd` вместо `npm`.

История миграций защищена контрольными суммами.
Уже применённые миграции пропускаются при повторном запуске.
Ожидающие миграции выполняются одной транзакцией: ошибка откатывает весь
текущий запуск.

## Развёртывание и проверка

Совместно с backend-разработчиком подготовлена серверная база `dicebound_dev`.
Перед развёртыванием пользовательские таблицы отсутствовали.
Подключение проверено через DBeaver и скрипт проекта.

17 октября 2026 года на сервере:

1. Успешно применены все четыре миграции.
2. Выполнен seed двух систем и схем.
3. Через DBeaver подтверждены JSON-объекты схем и количество секций: 3 для
   D&D, 4 для Call of Cthulhu.
4. Успешно повторён seed.
5. Пройдены все 21 автоматическая проверка, без ошибок и пропусков.

Проверки хранения выполнялись в отдельной временной схеме PostgreSQL, которая
удаляется после завершения.
Рабочие таблицы и seed-данные в `public` сохранялись.

| Проверка | Результат |
| --- | --- |
| Изначально пустая серверная БД | Таблицы созданы миграциями |
| Seed и повторный seed | Успешно, отсутствие дубликатов проверено |
| Общий контракт SheetSchema | Проверки формата обеих схем пройдены |
| Ограничения и сценарии хранения | Все проверки пройдены |
| Откат и атомарность миграций | Проверки пройдены во временной схеме |

Проверены JSONB, внешние ключи, уникальность, история, VIEW, EDIT и удаление
импортированной системы из доступных.

Дополнительно локально пройдены 5 тестов backend, lint без ошибок и
предупреждений и сборка.
Подготовлена конфигурация CI с PostgreSQL 17; результат запуска CI на GitHub в
этот отчёт не включён.

## Передача для дальнейшей интеграции

Для воспроизведения результата подготовлены миграции, seed, скрипты запуска,
тесты, инструкция и изменения команд и зависимостей backend-проекта.
Их необходимо передать backend-разработчику согласованным способом вместе с
учётом миграций, уже применённых на сервере.

Подключение PostgreSQL к NestJS и слой доступа к данным относятся к
[PostgreSQL integration — DiceBound-backend #6][pg-task].
Auth, Game Systems, Characters, History и Sharing используют подготовленную
модель для своих API и бизнес-операций.

Авторизация, хеширование паролей, проверка значений по SheetSchema, вычисление
формул и интеграция с renderer относятся к последующим сервисным задачам.
В рамках этой работы проверены модель хранения и общий контракт данных для
renderer.
