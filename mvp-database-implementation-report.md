# DiceBound MVP: реализация базы данных и переход на Prisma

Документ фиксирует исходное развёртывание БД от 17 октября 2026 года и
состояние перехода на Prisma Migrate на 23 октября 2026 года.
Команды и пути приведены относительно корня `DiceBound-backend`.

## Состояние перехода на 23 октября 2026 года

Реализация моделей, миграций, seed и тестов под Prisma представлена в
[PR backend №22][pr22].
На момент проверки PR открыт и ещё не включён в `main`.
Код в PR и состояние серверной БД учитываются отдельно.

В описании PR Рома указал, что структура существующей БД проверена чтением,
baseline и архивирование старой истории выполнены вручную.
Команда дополнительно подтвердила целевую БД: `dicebound_dev`, схема `public`.
Эти сведения зафиксированы со слов исполнителя и команды; повторная
инспекция серверной БД при обновлении этого отчёта не выполнялась.

После регистрации baseline миграциями этой схемы управляет Prisma Migrate,
история хранится в `_prisma_migrations`.
Старая история `schema_migrations` архивирована; собственный SQL-runner
больше не используется для дальнейших изменений.
Повторная регистрация уже выполненного baseline не требуется.

Порядок миграций, seed и перехода существующей БД описан в
[инструкции backend из PR №22][backend-guide].
Ссылка закреплена на версии файла из проверенного коммита PR.
Отдельный файл `database-prisma.md` в DiceBound-docs для этого отчёта не нужен.

## Миграции и модель хранения

В PR №22 подготовлена следующая структура миграций:

| Каталог | Сущности |
| --- | --- |
| `prisma/migrations/001_users/` | User |
| `prisma/migrations/002_game_systems/` | GameSystem, SheetSchema |
| `prisma/migrations/003_characters/` | Character, CharacterVersion |
| `prisma/migrations/004_character_shares/` | CharacterShare |

Каждый каталог содержит `migration.sql`.
Общий `migration_lock.toml` задаёт PostgreSQL.
В `prisma/schema.prisma` описаны шесть моделей с сохранением имён таблиц и
колонок через `@map` и `@@map`.

Существующая SQL-модель и перенос в Prisma сохраняют:

- UUID, timestamptz и JSONB для схем, данных персонажей и снимков;
- уникальность email через `lower(btrim(email))`;
- обязательный непустой `password_hash`;
- `source`, `builtin_code` и владельца для BUILTIN/IMPORTED;
- принадлежность схемы игровой системе через составной внешний ключ;
- положительный уникальный номер версии внутри персонажа;
- уникальность пары «персонаж / получатель»;
- неизменяемость схем, снимков и происхождения копии;
- обновление `updated_at` триггерами PostgreSQL;
- `history_visible` для VIEW и ограничения передачи EDIT.

Триггеры, функции, CHECK и индекс нормализованного email находятся в SQL
миграций и не заменяются одним описанием Prisma-моделей.

Импортированная система исключается из доступных через `deleted_at`.
Её схемы, существующие персонажи и история сохраняются.
Для независимой копии предусмотрены `source_character_id`,
`source_owner_id`, `source_owner_username` и `copied_at`.
Удаление оригинала очищает ссылку на него, сохраняя копию и её историю.

Создание первой версии, сохранение, restore и передача EDIT выполняются
сервисами в транзакциях.
Миграции не создают снимки или копии автоматически.
Авторизация, хеширование, валидация по SheetSchema и вычисление формул
относятся к сервисному слою.

## Seed

В PR №22 seed перенесён в `prisma/seeds/builtin-systems.json` с сохранением
фиксированных UUID систем и схем.

| Код | Схема | Секций |
| --- | --- | --- |
| `dnd-5e-mvp` | D&D 5e MVP v1 | 3 |
| `call-of-cthulhu-mvp` | Call of Cthulhu MVP v1 | 4 |

Схемы используют общий формат `sections → fields` и типы `text`, `number`,
`select`, `checkbox`, `resource`, `calculated`.
Это упрощённые листы MVP.

Seed запускается отдельно командой `npm run db:seed`.
В `prisma.config.ts` задан исполнитель `prisma/seed.mjs`, использующий `pg`.
Вставки и проверки выполняются в одной транзакции seed.
Повторный запуск не обновляет существующие записи и их даты.
Расхождение опубликованных данных вызывает ошибку с откатом вставок.
Пользователи, персонажи, версии и записи доступа seed-командой не создаются.

## Команды проекта

Для команд ниже нужна версия backend, содержащая изменения PR №22.
Параметр подключения Prisma CLI, seed и приложения — `DATABASE_URL`.
Пароли и локальные файлы окружения в документацию не включаются.

Проверка схемы, генерация клиента и статус миграций:

```sh
npm run db:validate
npm run db:generate
npm run db:migrate:status
```

Создание новой миграции в выделенной среде разработки:

```sh
npm run db:migrate:dev -- --name migration_name
```

Применение готовых миграций на сервере и отдельный запуск seed:

```sh
npm run db:migrate:deploy
npm run db:seed
```

`db:generate` не применяет миграции и не запускает seed.
`migrate dev` предназначен для среды разработки с shadow database.
Для общей серверной БД используются готовые миграции через deploy.

## Baseline существующей БД

Baseline и архивирование старой истории для `dicebound_dev.public` уже
выполнены вручную Ромой, согласно описанию PR №22 и подтверждению команды.
Этот факт заменяет прежнее утверждение отчёта, что серверный baseline ещё
не проводился.

Для переноса другой существующей БД требуется отдельная сверка структуры и
истории с миграциями backend.
Нельзя переносить сведения о baseline одной БД на другую.
Общий порядок приведён в [инструкции backend][backend-guide].

`migrate resolve --applied` регистрирует подтверждённую историю, но не
сверяет структуру и не выполняет SQL миграции.
`schema_migrations` и `_prisma_migrations` имеют разные форматы;
архивирование старой таблицы не означает её простого переименования.
Повторный baseline, `migrate reset` и `db push` не входят в порядок
проверки уже переведённой серверной БД.

## Исправления применённых изменений

Prisma Migrate не запускает старые `down.sql` автоматически.
В PR они сохранены в `prisma/manual-rollback/` как справочные скрипты.
Они удаляют таблицы и данные и не согласуют историю Prisma автоматически.

Исправления успешно применённых изменений оформляются новыми миграциями.
Для восстановления потерянных данных используется резервная копия.
Общая транзакция на весь запуск deploy не обещается.
В начальных SQL-миграциях PR заданы `BEGIN` и `COMMIT` для каждой миграции.
Ошибка следующей миграции не отменяет предыдущие успешно применённые.

Интеграционные `test:db` в PR отмечены как не запускавшиеся.
Выполнение baseline не считается выполнением этого набора тестов.

## Историческое развёртывание: 17 октября 2026 года

Первоначальная реализация использовала четыре пары `.up.sql` / `.down.sql`,
собственный runner и таблицу `schema_migrations`.
Подключение задавалось переменными `PG*`.
Runner применял все ожидающие миграции в одной транзакции и предоставлял
команду отката через `.down.sql`.
Это поведение старого механизма, а не Prisma Migrate.

17 октября в изначально пустой серверной базе `dicebound_dev`:

1. Применены все четыре миграции.
2. Добавлены две встроенные системы и схемы с 3 и 4 секциями.
3. Повторный seed выполнен успешно без дубликатов.
4. Пройдены 21 автоматическая проверка старой реализации.
5. Проверки хранения выполнены во временной схеме с её удалением.

Результаты сохранены как история выполненной работы.
Последующие baseline и архивирование истории отражены выше отдельно.
