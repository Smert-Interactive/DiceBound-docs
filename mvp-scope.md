# DiceBound MVP

Документ фиксирует утверждённый scope MVP DiceBound.
Он является основным источником scope продукта для roadmap,
дизайна и технических контрактов.

DiceBound MVP — schema-driven платформа для цифровых листов персонажей.
Разные НРИ описываются данными или импортируются из JSON.
Пользователь создаёт и редактирует персонажей, использует вычисляемые поля,
хранит локальную историю состояний и откатывается к старой версии.
Персонажем можно поделиться с правом `VIEW` или передать копию через `EDIT`.

> Status: Active

## Цель

MVP проверяет одну архитектурную гипотезу.

> **Важно:** новая НРИ подключается через новую `Sheet Schema` без создания
> отдельного frontend-компонента листа и без изменения основной логики
> `Character`.

`Sheet Schema` — декларативное описание структуры листа персонажа.
`Dynamic Sheet Renderer` строит интерактивный лист из пары `Sheet Schema` и
данных персонажа.
Frontend не содержит отдельный компонент листа под каждую НРИ.

Недопустимый подход:

```tsx
if (system === "dnd") {
  return <DndCharacterSheet />;
}
if (system === "coc") {
  return <CallOfCthulhuSheet />;
}
```

Правильная модель:

```text
Sheet Schema + Character Data → Dynamic Sheet Renderer → интерактивный лист
```

## Основной пользовательский сценарий

1. Регистрация или вход.
2. Просмотр списка персонажей.
3. Создание персонажа с выбором игровой системы.
4. Работа с листом, построенным `Dynamic Sheet Renderer`.
5. Редактирование данных и автоматический пересчёт `computed fields`.
6. Сохранение, которое создаёт новую `CharacterVersion`.
7. Просмотр истории и восстановление старой версии.
8. Выдача доступа `VIEW` или `EDIT` другому пользователю.
9. Импорт новой НРИ из JSON-схемы и управление игровыми системами.

## Функциональные требования

### Авторизация

MVP поддерживает регистрацию по email и паролю, вход,
выход и получение текущего пользователя.
Пароль содержит не меньше 8 символов.
При регистрации пароль вводится повторно.
После входа пользователь попадает на `/characters`, после регистрации —
на пустой список персонажей.

Пользовательские маршруты защищены авторизацией.
При истёкшей сессии пользователь переходит на вход и после входа возвращается на
ту же страницу.

### Список персонажей

После входа пользователь видит страницу «Персонажи» и кнопку
«Создать персонажа».
Страница состоит из двух блоков.

- «Мои персонажи» — собственные персонажи и копии, полученные через `EDIT`,
  с подписью «Копия от … · редактируется независимо».
- «Доступные мне» — персонажи с доступом `VIEW`,
  с подписью владельца и чипом `VIEW`.

Для каждого персонажа отображаются имя, игровая система,
дата последнего изменения и кнопка открытия.
Кнопка удаления есть только у собственных персонажей.
Без персонажей страница показывает пустое состояние с кнопкой
«Создать персонажа».

Удаление персонажа требует подтверждения.
При удалении удаляются лист, вся история версий и выданные доступы.
Копии, переданные другим пользователям через `EDIT`, остаются у них.

### Создание персонажа

Создание выполняется в три шага на одном экране: игровая система,
`Sheet Schema`, имя.
Шаг выбора системы содержит ссылки на управление системами и на импорт из JSON.
Поля листа заполняются значениями по умолчанию из схемы.

После создания система:

1. создаёт `Character`;
2. создаёт начальный `Character.data`;
3. создаёт `CharacterVersion` №1;
4. открывает динамический лист персонажа.

### Игровые системы

Для проверки универсальности движка MVP содержит две встроенные системы с разной
структурой.
Полная реализация правил этих систем не требуется.

D&D 5e (упрощённая):

| Группа полей | Поля |
| --- | --- |
| Основные поля | имя, уровень 1–20, класс из списка |
| Характеристики | STR, DEX, CON, INT, WIS, CHA, значения 1–30 |
| Ресурсы | HP, AC |
| Дополнительно | модификаторы характеристик как `computed fields` |

Call of Cthulhu (упрощённая):

| Группа полей | Поля |
| --- | --- |
| Основные поля | имя, профессия, возраст |
| Характеристики | STR, CON, DEX, INT, POW, APP, EDU, SIZ, значения 1–99 |
| Ресурсы | HP, Sanity, Luck |
| Дополнительно | навыки, например Spot Hidden, Library Use, Listen |

Пример вычисляемого поля D&D 5e: `modifier = floor((stat - 10) / 2)`.
При `STR = 16` модификатор равен `+3`.

Вторая система доказывает, что один renderer строит листы с разной структурой.

### Импорт игровой системы

Пользователь добавляет новую НРИ импортом JSON-схемы на странице
`/systems/import`.
Импортированная схема использует тот же формат `Sheet Schema`,
что и встроенные системы.
Импорт не может добавить новый тип поля.

Пользователь указывает название системы, название листа и JSON-схему.
Схему можно вставить текстом или загрузить `.json`-файлом.
Под редактором отображается статус синтаксиса JSON.

Схема проверяется по кнопке «Проверить схему».
Ошибки проверки выводятся списком с номером строки, в которой найдена ошибка.
Для корректной схемы отображается сводка и предпросмотр листа через тот же
`Dynamic Sheet Renderer`.

После импорта новая НРИ появляется на шаге выбора системы при создании персонажа
с подписью «Импортирована».

### Управление игровыми системами

Страница `/systems` показывает встроенные и импортированные системы.
Для каждой системы отображаются название, источник и число персонажей на
системе.

Импортированную систему можно удалить, встроенную — нельзя.
Удаление требует подтверждения.
Удалённая система пропадает из выбора при создании персонажа у всех
пользователей.
Вернуть её можно только повторным импортом JSON.

Существующие персонажи на удалённой системе, включая персонажей других
пользователей, продолжают работать.
Их лист, формулы и история версий используют сохранённую `Sheet Schema`.

### Dynamic Character Sheet

`Sheet Schema` состоит из секций.
`section` — структурный элемент схемы, который содержит набор полей и сам полем
не является.
Поля внутри секции отображаются в порядке массива `fields`.

MVP поддерживает шесть типов полей.

| `type` | Значение |
| --- | --- |
| `text` | Строка |
| `number` | Число с ограничениями `min` и `max` |
| `select` | Одно значение из заданного списка `options` |
| `checkbox` | Булево значение |
| `resource` | Текущее и максимальное значение |
| `calculated` | Значение по формуле, пользователь не редактирует его напрямую |

Пример значения поля типа `resource` в данных персонажа:

```json
{
  "hp": {
    "current": 18,
    "max": 24
  }
}
```

Формулы являются частью `Sheet Schema`.
При изменении зависимого значения `calculated`-поле сразу пересчитывается на
клиенте.
Формулы поддерживают операции `+`, `-`, `*`, `/`, `()` и функции `floor`,
`ceil`, `round`, `min`, `max`.

> **Ограничение:** использование JavaScript `eval()` запрещено.
> Формулы выполняются через ограниченный expression engine.

Режим read-only для старой версии и для получателя `VIEW` реализуется тем же
renderer с флагом, а не отдельным компонентом.

### Сохранение

Версия создаётся только по нажатию «Сохранить», а не при каждом нажатии клавиши.
Невалидное значение поля блокирует сохранение.
«Отменить изменения» возвращает последнее сохранённое состояние.
При ошибке сохранения изменения остаются на листе, а версия не создаётся.

При сохранении backend:

1. проверяет владение персонажем;
2. валидирует данные по `Sheet Schema`;
3. вычисляет `calculated`-поля;
4. сохраняет новое состояние в `Character.data`;
5. создаёт новую `CharacterVersion`;
6. возвращает актуальное состояние.

### История версий

Страница персонажа содержит вкладки «Лист», «История» и «Доступ».
Вкладка «Доступ» отображается только владельцу персонажа,
в том числе владельцу копии, полученной через `EDIT`.

История показывает версии от новых к старым.
Для каждой версии отображаются номер и дата в формате `ДД.ММ.ГГГГ ЧЧ:ММ`.
Версия 1 подписана «создание персонажа».
Текущая версия помечена и не имеет действия «Восстановить».

Историческая версия открывается через тот же `Dynamic Sheet Renderer` в режиме
read-only.
На странице версии отображается номер текущей версии персонажа и доступно
восстановление.

### Восстановление версии

Восстановление возвращает персонажа к выбранной версии и удаляет все последующие
версии.
Действие необратимо и требует подтверждения.
Подтверждение перечисляет удаляемые версии.

При восстановлении версии `v4` из истории `v1`–`v7`:

1. данные snapshot `v4` копируются в `Character.data`;
2. версии `v5`, `v6`, `v7` удаляются;
3. `v4` становится последней актуальной версией.

```text
v1 → v2 → v3 → v4 → v5 → v6 → v7
                 └── restore

v1 → v2 → v3 → v4
```

### Sharing

Владелец выдаёт доступ другому зарегистрированному пользователю по email.
Управление доступом доступно только владельцу персонажа.

На вкладке «Доступ» владелец видит таблицу с почтой получателя, уровнем доступа,
видимостью истории и доступным действием.
Тип доступа и видимость истории задаются при выдаче и потом не меняются.
Чтобы изменить их, владелец отзывает `VIEW` и выдаёт доступ заново.

| Возможность | `VIEW` | `EDIT` |
| --- | --- | --- |
| Что получает получатель | Оригинал только для чтения | Собственная копия |
| Изменение данных | Нет | Да, в копии |
| История версий | Только если владелец открыл её | Собственная, с `v1` |
| Восстановление версий | Нет | Да, в копии |
| Управление доступом к оригиналу | Нет | Нет |
| Отзыв владельцем | В любой момент, с подтверждением | Невозможен |

#### VIEW

При выдаче `VIEW` владелец решает, показывать ли получателю историю версий.
По умолчанию история скрыта.
Получатель видит вкладку «История» только при открытой истории и не может
восстанавливать версии.
После отзыва `VIEW` персонаж пропадает из списка получателя.

#### EDIT

При выдаче `EDIT` система создаёт у получателя копию персонажа с именем
`{имя} (копия)`.
Копия получает текущее состояние листа и новую историю версий, начиная с `v1`.
Копия принадлежит получателю, редактируется независимо и не синхронизируется с
оригиналом.
Изменения в копии не изменяют персонажа владельца.

Выдача `EDIT` окончательна.
Копию нельзя отозвать, а запись о переданной копии нельзя удалить.
Перед выдачей интерфейс предупреждает о необратимости.

#### Ошибки выдачи доступа

Для почты без аккаунта показывается нейтральная ошибка, которая не раскрывает,
существует ли аккаунт.
Повторная выдача доступа пользователю, у которого он уже есть,
завершается ошибкой.

### Экраны

- `/login` — регистрация и вход.
- `/characters` — блоки «Мои персонажи» и «Доступные мне».
- `/characters/new` — создание персонажа: игровая система, `Sheet Schema`, имя.
- `/characters/:id` — страница персонажа с вкладками «Лист», «История»,
  «Доступ».
- `/characters/:id/versions/:version` — просмотр исторического snapshot в режиме
  read-only.
- `/systems/import` — импорт новой НРИ из JSON-схемы.
- `/systems` — список игровых систем и удаление импортированных.
- `/profile` — почта, дата создания аккаунта,
  число своих и доступных персонажей, выход.

Страницы 404 и 403 показывают один и тот же текст и не раскрывают,
существует ли чужой персонаж.

## Нефункциональные требования

Данные персонажа хранятся отдельно от описания структуры листа.
Динамические значения персонажа хранятся в PostgreSQL как `JSONB`.
Каждая `CharacterVersion` содержит полный snapshot персонажа.
История персонажа не зависит от конкретной НРИ.
История локальна и не хранит авторов изменений.

Архитектура допускает несколько версий одной схемы в будущем.
В MVP действуют правила:

1. персонаж ссылается на конкретный `sheet_schema_id`;
2. опубликованная используемая схема не меняется разрушительно;
3. новая несовместимая структура создаётся как новая схема;
4. migration engine является post-MVP задачей.

Интерфейс MVP — адаптивное веб-приложение.
Основной макет рассчитан на desktop, на меньшей ширине интерфейс
перестраивается, а не сжимается пропорционально.

| Режим | Ширина |
| --- | --- |
| Desktop | ≥ 1024 px |
| Планшет | 640–1023 px |
| Телефон | < 640 px |

Минимальная поддерживаемая ширина — 360 px.
Правила перестройки заданы для типов блоков и типов полей, поэтому любой лист,
собранный `Dynamic Sheet Renderer`, перестраивается одинаково для любой игровой
системы.
Перестройка меняет только число колонок и ширину полей,
порядок полей всегда берётся из массива `fields`.

## Не входит в MVP

- Авторизация — OAuth, вход через Google и Discord, 2FA, подтверждение email,
  восстановление пароля.
- Игровые системы — визуальный конструктор систем,
  пользовательский Schema Editor, marketplace, публичная библиотека шаблонов,
  полноценная миграция между версиями схем.
- Лист персонажа — drag-and-drop редактор, произвольная ручная раскладка,
  отдельные сложные подсистемы инвентаря и заклинаний, аватарки,
  загрузка файлов.
- История — visual diff между версиями, авторы изменений.
- Совместная работа — кампании, команды, группы, роли кампании, чат,
  WebSocket и realtime collaborative editing.
- Sharing — публичные ссылки, anonymous sharing,
  приглашение незарегистрированных пользователей, сложная ACL-модель.
- Платформа — мобильное приложение, брокер сообщений, Redis, Elasticsearch.

> **Примечание:** адаптивная веб-версия не является мобильным приложением и
> входит в MVP.

## Критерии готовности

### Пользовательский сценарий

MVP считается готовым, если выполняется сценарий:

1. Пользователь регистрируется.
2. Пользователь входит в DiceBound.
3. Пользователь видит список персонажей.
4. Пользователь создаёт D&D-персонажа.
5. Лист строится из `Sheet Schema`.
6. Пользователь меняет STR с 10 на 16.
7. STR Modifier автоматически становится `+3`.
8. Пользователь сохраняет персонажа.
9. После обновления страницы данные сохраняются.
10. Пользователь делает ещё несколько изменений.
11. Каждое логическое сохранение создаёт новую `CharacterVersion`.
12. Пользователь открывает историю.
13. Пользователь открывает старую версию.
14. Старая версия отображается read-only.
15. Пользователь восстанавливает старую версию.
16. Текущий `Character` получает данные выбранной версии.
17. Все версии, созданные после выбранной, удаляются.
18. Пользователь создаёт персонажа Call of Cthulhu.
19. Персонаж получает другую структуру листа через тот же renderer.
20. Пользователь импортирует новую НРИ из JSON.
21. Импортированная НРИ появляется в списке и позволяет создать персонажа.
22. Владелец выдаёт второму пользователю `VIEW`.
23. Второй пользователь видит персонажа, но не может его изменить.
24. Владелец выдаёт второму пользователю `EDIT`.
25. У второго пользователя создаётся отдельная копия персонажа.
26. Второй пользователь изменяет и сохраняет свою копию независимо от оригинала.
27. Изменения копии не меняют исходного персонажа владельца.

### Технический acceptance test

Разработчик добавляет третью игровую систему новой JSON-схемой.
После этого:

1. `Dynamic Sheet Renderer` на frontend не изменяется.
2. Основной backend-код `Character` не изменяется.
3. Новая система появляется в списке.
4. По новой системе можно создать персонажа.
5. Поля валидируются по новой схеме.
6. `calculated`-поля работают.
7. История версий работает.
8. Восстановление работает с удалением последующих версий.
9. Sharing `VIEW` работает для оригинального персонажа.
10. Sharing `EDIT` создаёт независимую копию персонажа.
11. Новую НРИ можно добавить импортом JSON-схемы.

Выполнение теста подтверждает основную архитектурную идею DiceBound.
